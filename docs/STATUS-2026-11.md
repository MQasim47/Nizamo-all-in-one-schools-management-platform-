### Next.js advisory exposure
The advisories cover the Image Optimization API (SVG RCE), Server Actions (DoS) and `use cache` (RCE / info disclosure). The app uses no `next/image`, no Server Actions and no `use cache`. **However** `next.config.js` sets `images.remotePatterns` to `*.supabase.co/storage/v1/object/public/**`, so the built-in `/_next/image` endpoint will fetch from *any* Supabase project's public bucket, including one an attacker creates. ## 4. Reliability gaps

The product will hold children's records, marks and money. What is missing today:

1. **No CI.** No `.github/workflows`; nothing runs lint, unit tests, build or tenant tests on push. Every check depends on someone remembering to run it locally.
2. **Build blocked by the Next advisory** on a fresh machine (see §2). CI would fail until Next is upgraded.
3. **No tests for business rules yet**, because the rules don't exist yet: GR numbering under concurrency, SLC data, marks totals/grades (`lib/utils/grades.js` is untested), fee arithmetic (discounts, fines, partial payments, carry-forward), attendance percentages. Each needs table-driven unit tests and a DB-level test.
4. **End-to-end browser tests are minimal**: `test:nav` covers marketing navigation only. No E2E for login → do the task → see the result for any role.
5. **Tests need a hand-started dev server on a fixed port** (`test:waitlist`, `test:app`, `test:nav`), which collides with other local projects (it did today). They should start their own server or run against a built `next start`.
6. **No error monitoring.** No Sentry or equivalent; server errors are invisible in production. `app/(dashboard)/school/error.jsx` shows a friendly message, but nobody is told.
7. **No structured logging policy** that guarantees no personal data in logs.
8. **Backups**: nothing in the repo about backups. Supabase free tier pauses when idle and has no point-in-time recovery; production needs a paid plan with PITR and a tested restore drill.
9. **Migrations are manual** (SQL editor), untracked, and have no down/rollback notes; migration 004 is proof that one gets forgotten. Need a `schema_migrations` table and a check that fails when the DB is behind the repo.
10. **`schema.sql` drifts from reality**: it still says 3 roles (line 35) while 002 changes it to 7; a fresh setup works only because 002 runs after it.
11. **Validation coverage**: zod on all 6 current write routes (waitlist, register, settings, admin waitlist, schools check/available). There is no shared pattern yet for the dozens of routes to come.
12. **Error handling is inconsistent**: routes return ad-hoc `{ error: '...' }`; there is no error code, no shared helper, and `lib/db/*` helpers `throw` raw Supabase errors (audit L9 also still open).
13. **Rate limits are in memory** (`lib/utils/rate-limit.js`), per server instance; on Vercel that is per lambda, so effectively weak. No per-IP login limit.
14. **CSP is still report-only** (`next.config.js:23`), with `'unsafe-inline'` scripts.
15. **Dates**: Pakistan-time helpers exist (`lib/utils/dates.mjs`), but the academic year is hard-coded (M9).
16. **Open audit items** (`docs/AUDIT.md`): M3 (first-login password change / reset), M7 (approvals count; returns with exams), M8 (partially fixed: helpers exist, DB defaults still UTC), M9 (academic year), L4/L5 (resolved by the Session 5 shell once merged), L9 (`getSchoolSettings` swallows errors), L11 (`UNIQUE(email, school_id)` with NULL school), L12 (unused env vars). Plus new: Next critical advisory, zod high advisory, `images.remotePatterns` wildcard.
17. **Audit coverage gaps**: attendance and homework have no audit trigger; CLAUDE.md requires audits on marks, fees, GR, roles and settings (all covered), but attendance edits matter to parents too.
18. **No idempotency** for money writes (a double-click on "record payment" would create two payments). Needs idempotency keys or unique constraints from the start of the fees module.
19. **Single developer environment = single dev database**: tests seed and delete throwaway schools in the same project as the demo data. A separate test project (or local Supabase via CLI/Docker) is safer.

## 5. Mobile-app readiness

Target: a parent/teacher app for attendance, results, fee alerts and push notifications, built after the web is complete.

### What exists
- Tenant isolation lives in Postgres (RLS + `app.school_id()` + `app.can()`), not in React pages. Any client that reaches the DB through `getSchoolClient`-style tokens is isolated the same way. This is the best possible starting point.
- Route handlers already use one pattern: `requireApiSession(permission)` → zod → `lib/db/*`.
- The permission model already includes `parent` and `student` roles and `user_students` links.

### What is not ready
1. **Auth is cookie-only.** `requireApiSession` calls NextAuth `getServerSession`, which reads a browser cookie. A mobile app cannot use that cleanly. Needs a bearer-token path.
2. **Almost no API.** School data is read directly in server components (`lib/db/dashboard.js`), so the mobile app would have nothing to call. Every module from now on must expose route handlers.
3. **Identity is email + password + subdomain.** Pakistani parents mostly have a phone number and WhatsApp, not an email they remember. `users.email` is required.
4. **No guardian/family model**: one parent with three children in two schools (or one school) is not represented beyond `user_students` rows.
5. **No notification design**: no table, no outbox, no device tokens, no provider.

### Decide NOW (before Session 7), so the web build does not have to be redone
1. **API-first rule.** Every module's reads and writes go through a service function (`lib/services/<module>.js`, takes `ctx`, validates with zod), called by both the web page and a versioned route handler under `/api/v1/...`. No Server Actions for data writes. Pages may call services directly; mobile calls the route.
2. **One error envelope and status codes** for all `/api/v1` routes: `{ error: { code, message, fields? } }`, 400/401/403/404/409/422/429/500. Cursor pagination (`?cursor=&limit=`) for lists.
3. **Auth abstraction**: `requireApiSession` accepts either the NextAuth cookie (web) or `Authorization: Bearer <access token>` (mobile). Mobile tokens: short-lived access token (15 min) + rotating refresh token stored hashed in a `device_sessions` table (user, device id, platform, last seen, revoked_at) so a school can sign a lost phone out. Same DB re-check (active user, active school) as today.
4. **Phone identity for parents**: allow `users.phone` (normalised +923…, `lib/utils/phone.mjs` exists) as a login identifier, unique per school; plan OTP (WhatsApp/SMS) login for parents. Make `email` nullable for parent/student roles. Decide this before the Students module creates guardians.
5. **Guardian/family model** shared by Students (guardians on the General Register), Fees (family accounts, sibling discounts) and the parent app: `families` + `guardians` + `student_guardians`, and a parent `users` row links to a `guardian`. Design it once in the Students session.
6. **Notification architecture**: a `notifications` table (per recipient, what/when/read) and a `notification_outbox` (event, channel, payload, status, attempts, provider message id) written by the service layer in the same transaction as the event (e.g. absent marked). A worker (Vercel Cron or Supabase Edge Function) sends via WhatsApp now and push (FCM/Expo) later, from the same outbox. `device_tokens` table added when mobile starts. Per-guardian channel preferences and opt-in (WhatsApp Business rules).
7. **Shared validation and labels**: zod schemas in `lib/validation/*` and English/Urdu label keys kept free of React so a React Native app can import them.
8. **Times and money**: store UTC timestamps, school-local dates as `date`, money as integer rupees (no floats) — the mobile app will show the same numbers.
9. **Rate limiting and caching in a shared store** (Upstash Redis) because mobile traffic will hit many server instances.

## Definition of Done (every module, before merge to main)

A module is done only when all of these are true. If one is skipped, say so in PROGRESS.md and ask before merging.

   - audit test: a change writes one `audit_log` row with old and new values.
5. **States**: every page has loading, empty (says what to do next) and error states; every destructive action confirms and is reversible where possible.
6. **Language**: plain English labels; Urdu where it matters (printouts, parent-facing text); no jargon.
7. **Privacy**: sensitive fields masked in lists; no personal data in URLs, logs or error messages.
8. **Mobile-ready**: anything a parent or teacher will do on a phone is reachable through `/api/v1` with bearer auth, paginated, and works at 360px on the web.
9. **Green pipeline**: `npm run lint` (0 errors), all test scripts, `npm run build`, CI green.
10. **Docs**: PROGRESS.md updated (done, decisions, known issues, next); CLAUDE.md updated if a rule or command changed.

## Reliability rules

- **Money is integer rupees** (`bigint`), never floats. Every fee calculation is a pure function with unit tests; totals are recomputed in SQL and compared in tests.
- **Marks and grades** are computed by one pure function (`lib/utils/grades.js` rules from the PHP MVP) with tests; stored results never change without an audit row; approved results are locked.
- **Idempotent writes** for payments, challans, imports and messages: an idempotency key or a unique constraint, so a double click or retry never creates a duplicate.
- **Transactions** for anything that touches more than one row that must stay consistent (Postgres function/RPC), never several client calls in a row.
- **Migrations are forward-only and additive**: add columns/tables first, backfill, then switch code, then remove in a later migration. Every migration is applied to dev and recorded in `schema_migrations`; `check:db` fails when the DB is behind the repo. Never edit an applied migration.
- **No silent failures**: helpers throw typed errors; route handlers map them to the error envelope; unexpected errors go to error monitoring (without personal data).
- **Dates**: school dates are Pakistan dates (`lib/utils/dates.mjs`); never `toISOString().split('T')[0]`. Academic year comes from the school's current session, never a literal.
- **Every bug gets a regression test** before the fix is merged.
- **CI is the gate**: nothing merges to main with a red pipeline; no `--no-verify`.
- **Dependencies**: `npm audit` has no critical/high findings at merge time; security patches are applied within a week.
- **Backups**: production runs with point-in-time recovery; a restore is rehearsed before launch and every quarter.
